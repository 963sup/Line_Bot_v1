# Actions internal runtime
Build workspace dependencies first. `pnpm actions:run` accepts stdin JSON with a verified LINE `proof` and `operation`: `execute` plus `command`, `rules` plus `repositoryId`, or `run` plus `repositoryId/id`. Commands use `define / execute / retry / cancel`, `requestId`, `expectedVersion` and Repository scope. Never place proof in argv, logs or committed files.

`pnpm actions:worker` accepts `{"limit":20}` on stdin, processes at most that many event claims/run steps and exits with a structured count. It is an operator process using the existing restricted database runtime identity; it accepts no user/role override. Run it only against the intended environment. There is no scheduler or daemon.

Uses existing `APP_ORIGIN` for the HTTPS `/notifications` link and `LINE_CHANNEL_ACCESS_TOKEN` for delivery. Missing LINE configuration reports unavailable independently of Inbox creation. See [Actions contract](../../docs/owners/actions.md). Production activation and real-recipient testing are separate operator actions.

## Isolated acceptance

Run `pnpm exec turbo run test --filter=@line_bot_v1/actions` from the repository root. Turbo builds the public Actions/LINE exports and their dependencies before testing, including on a fresh checkout; a direct package `test` invocation assumes those builds already exist. The suite includes the actual host composition, declarative schemas in disposable PGlite, WBS publication, the LINE protocol adapter and Inbox read/mark-read use cases. It replaces the environment with synthetic configuration and intercepts every fetch; it neither loads root secrets nor contacts LINE. The scenario loses the first provider response, reconstructs the runtime, receives accepted HTTP 409 using the same persisted payload/key, and verifies one authorized Inbox item. Existing owner tests cover replay, disable/revocation, cancellation and expired leases; CI additionally requires disposable PostgreSQL for independent-session competition.

This proves the internal data/provider-contract flow. It does not prove deployed credentials, browser rendering, scheduler execution or device delivery.

## Controlled environment acceptance

1. Record the exact deployed revision, environment, test Repository, authorized manager and canonical recipient IDs. Use a dedicated Repository and explicitly approved recipients: the worker consumes all eligible pending events/runs in its database, not just the test Repository. A limit bounds work; it does not isolate scope. Confirm the target environment has no unrelated eligible work before invoking it.
2. Build workspace dependencies. Supply current LINE proof through protected stdin to `actions:run`; never place proof in argv, shell history or evidence. Define an enabled `notify-wbs-baseline` rule with `expectedVersion: 0`, a fresh UUID `id`/`requestId`, and the approved explicit recipient list. Read back with operation `rules`. Enable before publication; old events are intentionally excluded.
3. Publish a valid WBS proposal through the existing authorized WBS flow. Record its Repository/Baseline/Revision IDs. Invoke `actions:worker` once with stdin `{"limit":1}` and read its structured result. This may only accept the event; remaining work requires another bounded invocation. Do not interpret a zero finished count as notification failure.
4. Obtain the resulting Run ID from the intended environment using authorized operator read-only evidence, then query `actions:run` with operation `run`, Repository ID and Run ID. Inspect the frozen rule/recipient version, attempts and each step result. If `waiting`, respect `due`; a fresh worker process resumes the persisted step. Do not create a new rule or Run to retry an uncertain send.
5. Sign in as the test recipient and open `/notifications`; verify exactly one item bound to the recorded Baseline/Revision, then mark it read. Repeat a bounded worker invocation and confirm no duplicate item. In an isolated test environment, verify current access revocation removes read/mark-read access and rule disablement stops subsequent steps. Preserve already established effects.
6. Record Inbox creation, LINE provider acceptance and device observation separately. Missing configuration is unavailable; an unresolved timeout remains unknown. Stop the test rule using `define` with its current version and `enabled: false`, a fresh request ID and the same definition. Read back disabled state. Disabling a rule does not delete Inbox items or undo an accepted message.

Production activation and real-recipient sends require an exact environment and recipient authorization. Retain redacted counts/statuses and revision/source identifiers as evidence; do not retain proof, access tokens, LINE targets or message payloads. Persistent scheduling is a separate decision after this acceptance flow succeeds.
