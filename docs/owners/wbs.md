# WBS

Baseline publication atomically saves a version-bound outbox event. The public event feed exposes leased claim/acknowledge and a Project event cursor; rule activation reads that cursor under the same current Project scope decision. Consumers commit deduped acceptance before acknowledging. Runtime cannot update event payload; lease expiry permits redelivery with the same Baseline/Revision identity.

The owner-published metrics query reports current OPEN proposals, the published Baseline and structural draft differences under current Project access. Missing content remains uninitialized; without a published Baseline, differences are null rather than an invented approved scope. Consumers use these facts without acquiring WBS authority.

WBS owns a Project-scoped work decomposition document, its head version, immutable Revision content/history, governance, Baselines and durable exact-replay receipts. Project owns the enclosing Project's current authorization and lifecycle. WBS is a local product capability and does not redefine GitHub GitObject, Commit, PullRequest or ProjectItem semantics. [Resources](resources.md) owns Repository-native resources and is distinct from GitObject. WBS-to-Resources integration remains subsequent work and does not transfer WBS or Project authority.

## Authority and invariants

- Project owns identity, current `READ | WRITE | ADMIN` access and open/closed/deleted lifecycle. WBS consumes Project's public content-scope contract and never queries Project private authorization tables.
- Read follows current Project `READ`, including historical content. Draft edit, proposal and review require `WRITE | ADMIN`; policy changes, Baseline publication and fixed Actions require `ADMIN`. Public visibility is read authority only. A closed Project remains readable and permits authorized exact replay, but rejects new writes; a deleted Project is not found.
- One Project has at most one WBS head. Immutable schema-versioned Revision documents are the only scope content authority; the head points to one matching version/revision. No second mutable node store exists.
- Node identity survives rename/reparent/reorder. WORK_PACKAGE is a leaf; DELIVERABLE is a decomposition container. Reject duplicates, cycles, missing parents and depth over 32; maximum 1000 nodes. Position is normalized among siblings; displayed numbering is derived.
- Draft content may omit deliverable/acceptance text. A saved revision is not approval, acceptance or Baseline.
- Each committed command advances WBS version once and atomically inserts a Revision and receipt. Stale versions and reuse of requestId with different content conflict. Replay rechecks current qualification/access before returning the prior receipt.
- Initialization is explicit. Reads never create WBS content. Subtree deletion is explicit and historical documents remain immutable.
- Issue owns assignment, execution and workflow. Project owns planning context and current access/lifecycle; only WBS edits WBS scope facts.
- The former per-line `import-contract` command is retired. A whole immutable Content revision initializes an empty Project WBS draft through Content's public transaction-bound reader. WBS applies the fixed `content-wbs-v1` hierarchy projection once and retains Content node/source-row coverage on the immutable WBS revision. This requires disclosure confirmation and never publishes a Baseline implicitly. Historical WBS revisions and the private `contract_import` column remain readable until an independently controlled retention/cutover decision; no schema reconciliation deletes or rewrites them. Project governance/Baseline publication remains separate.
- R1 retains Repository-scoped WBS source/schema/capabilities only as a transfer boundary for existing durable facts. `wbs_scope_transfers` records immutable source snapshot and `REQUESTED | ACTIVE | CANCELLED` cutover evidence; `legacy_wbs_command_evidence` binds migrated request identity/fingerprint/Revision to the activated transfer so replay cannot silently become a new Project command. Only `REQUESTED | ACTIVE` reserve a Repository and Project, so an owner-withdrawn `CANCELLED` intent permits a corrected request while preserving the old evidence. A Project WBS scope is unavailable while its transfer is requested. No dual write or permanent legacy coexistence is allowed; final removal requires verified transfer/readback.

## Delivery

Source roles are explicit: shared `domain/document.ts`, `domain/content.ts`, `domain/governance.ts` and `domain/scope-governance.ts` own pure WBS rules; `domain/policies/project-access.ts` maps the Project role contract. Project-scoped Application, DTO, Repository Port, metrics and Baseline-event files use the `project-` prefix in their existing role directories. PostgreSQL adapters implement those ports; composition exposes only their contract types. Public consumers use the corresponding explicit exports.

Runtime owner: `packages/wbs`. Project Web transport uses stable Project identity, delegates current scope decisions to Project, and exposes current content, immutable history and governance without creating another WBS owner.

Project is the Web entry for new WBS. Repository Web retains existing source content/history, commands, exact retries and transfer recovery, but no longer offers initialization. After cutover retires the Repository content API with 410, the legacy page resolves its current Repository locator under current access and reads the source owner's durable transfer before linking to the ACTIVE Project WBS. An unauthorized, unavailable or unresolved lookup never exposes a remembered destination. REQUESTED is pending, not completed; Web cannot activate it.

Repository Overview consumes a WBS-owned read-only legacy-entry query. The query rechecks the current actor and Repository read scope, then returns only `entryRequired`: true when durable source content/history/receipt evidence exists or when that actor has a live `REQUESTED | ACTIVE` transfer. A `CANCELLED` intent alone is not an entry reason, and no destination Project identity crosses this overview boundary. Durable transfer evidence remains readable after the Repository content API and its source tables retire; unavailable evidence is reported as unavailable by the Web consumer rather than as absence.

The R1 transfer request requires the current active User to own/administer a public source Repository and the same User to own/administer an open private target Project without collaborator grants. In the same exclusive-governance transaction, it binds the exact source version/head/hash/counts and preflights the empty target plus zero governance, outbox, Actions and Notification dependencies. Source writes remain available while `REQUESTED`; therefore trusted Release execution rechecks source ownership, target eligibility, dependency emptiness, destination emptiness and the unchanged snapshot before activation. A mismatch aborts atomically and leaves the request recoverable.

Authenticated GET returns only the current source owner's live `REQUESTED` or `ACTIVE` intent. That current source User owner may withdraw `REQUESTED` with a separate exact-replay request ID even if source visibility/archive state changed or target Project authority/lifecycle disappeared; cancellation never depends on target access. Withdrawal changes only state, cancellation time and cancellation request identity. It cannot rewrite the captured snapshot, cannot cancel `ACTIVE`, and releases the live Repository/Project reservation for replanning. Release execution alone may activate after exact main/deployment/provider-recovery checks; Web never activates or dual-writes the destination.

Commands require `requestId`, `projectId`, `expectedVersion` and exactly the fields of the selected action. Actions: initialize, create-node, update-node, move-node, delete-subtree. Initialization expects version zero. All other commands require an existing WBS. Update-node edits content/type only; structural changes use move-node. Errors distinguish input, access, missing resource, version/replay conflict and unavailable/unknown result.

## Scope governance

The Project WBS governance transport owns proposal, policy, review and Baseline exchange. Queries accept stable Project identity and optional proposalId, baselineId, beforeProposal or beforeBaseline; proposalVersion and beforeReview require proposalId. Proposal/Baseline/review lists use keyset pagination; detail reads always remain Project-scoped. Reads never initialize governance state.

- Draft content head/version stays independent from governance version. Governance commands never fabricate a content Revision or overwrite a later draft.
- Create/revise Proposal freezes a same-Project candidate Revision and the current nullable base Baseline. Immutable ProposalVersion snapshots preserve the exact title/reason/base/candidate/status and actor reviewed previously; the Proposal head selects one snapshot. Revise increments proposal version and invalidates older reviews; close and publish are terminal. Historical proposal versions remain read-only. Proposal numbers and Baseline numbers are stable governance sequence locators and may contain gaps.
- Review binds proposal version, candidate Revision and policy version. Only the latest review by each reviewer for that tuple counts. A currently eligible request-changes review blocks publication. Publication rechecks active qualification and current Project `WRITE | ADMIN` for every counted reviewer under the Project transaction locks.
- Default policy is at least one approval with self-approval allowed. When disabled, neither the original creator nor the current proposal version's proposer may supply approval. Current Project `ADMIN` may change the approval count (1–10) and self-approval policy; immutable policy versions remain readable and old-policy reviews do not authorize a new publication.
- Project `WRITE | ADMIN` may create/revise/close proposals and review them. Only `ADMIN` may publish or set policy. All commands require requestId and expected governance version; proposal commands additionally bind expected proposal version, and review/publish/policy commands bind expected policy version. Exact replay rechecks current operation authority and may return its receipt while closed; new mutations fail while closed.
- First Baseline requires a reviewed proposal. Mandatory checks enforce a valid tree, at least one work package and each work package's nonempty deliverable/acceptance requirements. Incomplete drafts and proposals may be saved but cannot be published.
- Publication atomically persists immutable Baseline (including counted review IDs and policy version), marks Proposal published, advances the formal pointer and writes the exact-replay receipt. A changed formal base requires an explicit proposal update and fresh review. Two competing publications cannot overwrite each other.
- Baseline records approved scope, not completion or work-package acceptance. Immutable policy/review/Baseline/receipt relations grant no UPDATE/DELETE to the application role. Structural comparison reports changes by stable node identity, including parent/order/content.
- Historical proposal reads resolve publication by the reviewed proposal version, retaining the publication-time policy and approval evidence even after policy changes; the old OPEN snapshot status does not erase its published Baseline association.

Verification: owner domain/persistence tests, HTTP tests, browser checks and a CI-only disposable PostgreSQL 17 multi-session race test. Local runs without `WBS_TEST_DATABASE_URL` explicitly skip that race test; CI requires it and disables WBS test-result caching. The test only accepts a loopback server and never uses production credentials.

## Subsequent delivery contract

1. Scope governance above is implemented; subsequent work-package acceptance remains separate.
2. WBS references Issue execution and Discussion decisions by stable identity/version; reads recheck source access. Issue completion never automatically accepts a work package.
3. Project-scoped WBS is current without extending the FPT ProjectItem union. Repository-WBS cutover requires explicit mapping, replay preservation and recovery/readback evidence.
4. Evidence adds version-bound decisions, source references and protected attachments. Asset is a monetary value definition owner, not file storage.
5. Watch retains its three-state intent; committed-event outbox, deduplicated fan-out and current source access are required before notification delivery is claimed.
6. Structural comparison precedes branches/three-way conflict handling and same-Owner independent Forks. Fork never copies grants or private attachment access. Automation starts with fixed checks, without arbitrary code execution.

Items 2 and 4–6 are later delivery targets. Project scope, fixed Actions and explicit Project Baseline notifications are current R1 capabilities; their Repository predecessors remain only until transfer evidence is verified. No empty tables, writer surfaces or disabled UI shells are created for later targets.
